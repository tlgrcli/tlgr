# Telethon as the engine under tlgr — deep capability analysis

Scope: the **installed** package `/Users/p4/Projects/tlgr/.venv/lib/python3.12/site-packages/telethon` (Telethon **1.44.0**, TL **layer 227**, 800 request classes / 1662 constructor classes registered in `tl/alltlobjects.py`), compared with the repo snapshot at `scratchpad/refs/telethon` (version string 1.42.0, `telethon_generator/data/api.tl` = **layer 222**; the 1.42 tag itself shipped layer 216 per `readthedocs/misc/changelog.rst`) and with tdesktop's `mtproto/scheme/api.tl` (**layer 229**). ## 2. Raw-call cookbook

```python
from telethon.tl import functions as F, types as T
from telethon import utils
```

**Invoking.** `result = await client(F.messages.SomeRequest(...))`. Any argument annotated `TypeInputPeer/TypeInputUser/TypeInputChannel` may be given as an entity-like (int id, `@username`, `Peer`, `User`…) — the generated `resolve()` on the request calls `client.get_input_entity` and `utils.get_input_channel/user`. Lists of requests are sent in one container: `await client([req1, req2])` (results list; `MultiError` when any fails). `ordered=True` chains with `invokeAfterMsg`. Every request with a `random_id` param auto-generates it (`helpers.generate_random_long()`), every `hash: int` must be supplied (use `0` unless you implement the ETag algorithm from `docs/api/api__offsets.md`: `hash = hash ^ (hash >> 21); hash ^= hash << 35; hash ^= hash >> 4; hash += id` over the ids you already hold; `*NotModified` is returned when unchanged).

**Reading results.** Most list-returning types (`messages.Messages/MessagesSlice/ChannelMessages`, `messages.Dialogs/DialogsSlice`, `messages.ChatFull`, `users.UserFull`, `channels.ChannelParticipants`, `contacts.Contacts`, `contacts.Found`, `messages.PeerDialogs`, `Updates`) carry `.users` and `.chats` lists next to the payload; build a lookup `{utils.get_peer_id(x): x for x in r.users + r.chats}` (strip mark with `add_mark=False` if you need raw ids) — this is exactly what the client iterators do before `Message._finish_init(client, entities, input_chat)`. Feed every result to `client.session.process_entities(result)` (the client already does for `client(...)` calls) so access hashes are cached. `Updates` returned by mutating calls (`sendMessage`, `editMessage`, `updatePinnedMessage`, `channels.editAdmin`, `messages.sendReaction`…) contain the resulting `Update*` objects; `client._get_response_message(request, result, input_chat)` extracts the `Message` (used by `send_message`). `Bool` results are Python bools. `messages.AffectedHistory` (`pts, pts_count, offset`) must be re-invoked while `offset > 0` (e.g. `messages.deleteHistory`, `messages.readMentions`).

## 3. Events & update handling

**Pipeline** (`client/updates.py::_update_loop`, `_updates/messagebox.py`): the sender pushes every `Updates`-typed object into `_updates_queue`; `MessageBox.process_updates` checks `seq`/`pts`/`qts` per "entry" (account, secret, each channel) exactly as `docs/api/api__updates.md` prescribes, raising `GapError` → `updates.getDifference(pts, date, qts)` / `updates.getChannelDifference(channel, filter=ChannelMessagesFilterEmpty, pts, limit=100 for users/100000 bots)` are issued; `updatesTooLong` forces a difference; a 15-minute silence (`NO_UPDATES_TIMEOUT`) or 0.5 s unresolved gap (`POSSIBLE_GAP_TIMEOUT`) also trigger it. Difference errors: `PersistentTimestampOutdated/Invalid`, `ServerError`, `TimedOut`, `FloodWait` → end prematurely and retry later; `ChannelPrivate/ChannelInvalid` → stop tracking that channel; `Unauthorized/AuthKeyError` after having been logged in → `client.disconnect()` with `client._updates_error` set (surfaces from `run_until_disconnected()`); `TypeNotFoundError`/`sqlite3.OperationalError` → same (the "session misuse" path). Everything else is logged as "Fatal error handling updates (this is a bug…)" and the client disconnects.

**Own updates**: results of the client's own requests that are `Updates`/`UpdateShort*`/`AffectedMessages`-like are queued with `_self_outgoing=True`; they advance pts but are **filtered out before dispatch** (`messagebox.py:495`). Consequence: handlers in the same process never see messages/edits/deletes/reactions this client performed (e.g. a `tlgr message send` executed through the daemon will not fire the daemon's `NewMessage(outgoing=True)` handler; sends from other sessions will).

**Dispatch** (`_dispatch_update`): builds each event type once per update (`EventBuilderDict`), first feeds open `Conversation`s, then iterates `(builder, callback)` in registration order; `builder.resolve()` turns `chats=` into a set of marked ids (network if usernames); `filter()` may return an awaitable; exceptions in callbacks are logged (`Unhandled exception on <name>`) and swallowed; `events.StopPropagation` stops the chain. `sequential_updates=True` (tlgr's setting) processes one update at a time from an unbounded deque — a slow handler delays everything; default creates a task per update and (TODO in source) does not log failures of `_dispatch_update` itself.

**Catch-up / persistence.**
* `catch_up=True` in the constructor: at `connect()` the session's `update_state` rows are loaded into the MessageBox (row `id=0` → account `pts/qts/date/seq`; other rows → channel pts, only if the channel's access hash is cached, else warning "No access_hash in cache for channel …, will not catch up") and an `UpdatesTooLong` is queued so `getDifference` runs first thing. Without `catch_up`, `_on_login`/`get_me` → `updates.getState` + one `getDifference` initialise a fresh state (nothing missed while offline is replayed).
* `await client.catch_up()` at any time queues `UpdatesTooLong` (forces a full difference; also the documented way to "fetch new updates now").
* State is written by `_save_states_and_entities()` (called from `disconnect()` and when the in-memory entity cache exceeds `entity_cache_limit`), then `session.save()`; **not** on a timer. The self-user id is stored as a fake entity row `id=0, hash=<self id>`.
* `receive_updates=False`: every request is wrapped in `invokeWithoutUpdates`; `set_receive_updates(True)` re-subscribes with `updates.getState`.
* After an automatic reconnect `_handle_auto_reconnect` only calls `get_me()`; the catch-up code after it is unreachable (`return` before it). Gaps are then only closed by the 15-minute deadline or an explicit `catch_up()`.
* `MessageBox` internals are importable: `client._message_box.session_state()` → `(dict(pts,qts,date,seq), {channel_id: pts})`; `client._message_box.load(SessionState(...), [ChannelState(...)])`; `telethon._updates.Entity/EntityType` describe the cache format (`'U'/'B'/'G'/'C'/'M'/'E'`).

## 4. Sessions

**SQLite schema** (`sessions/sqlite.py`, `CURRENT_VERSION = 8`, file `<name>.session`, `sqlite3.connect(filename, check_same_thread=False)`, default 5 s busy timeout, rollback journal, commits only in `save()`/`close()`):

```
version(version integer primary key)
sessions(dc_id integer primary key, server_address text, port integer, auth_key blob, takeout_id integer, tmp_auth_key blob)   -- exactly ONE row (delete+insert on every change)
entities(id integer primary key, hash integer not null, username text, phone integer, name text, date integer)              -- id is the *marked* peer id (-100…)
sent_files(md5_digest blob, file_size integer, type integer, id integer, hash integer, primary key(md5_digest,file_size,type)) -- legacy; not populated in 1.44 (allow_cache is a TODO)
update_state(id integer primary key, pts integer, qts integer, date integer, seq integer)                                     -- id 0 = account, else channel id
```

Upgrades run automatically (v5→6 wipes `entities` because hashes may be wrong; v7→8 adds `tmp_auth_key`, only stored on disk when `SQLiteSession(store_tmp_auth_key_on_disk=True)`). `session.save_entities = False` disables caching. `SQLiteSession.list_sessions()` lists `*.session` in cwd only. Lookups: `get_input_entity(key)` accepts marked/unmarked ints, `Peer*`, `InputPeer*`, `@username`, phone, exact display name; username collisions evict the older row (1.44). The `entities` table is what makes `tlgr chat <id>` work for ids never seen in this process — tlgr should warm it (e.g. `iter_dialogs`) or resolve via its own store.

**Concurrency hazards** (two processes on one `.session` — which tlgr does today when `tlgr account add/import` and the daemon touch the same file, and would if a future "direct mode" bypasses the daemon):
1. Both processes derive the same `auth_key`; both open MTProto sessions with different `session_id`s from the same key. Telegram tolerates this, but updates are delivered to only one connection at a time ("last active connection", `docs/api/api__updates.md`), so the daemon's event stream silently loses updates whenever the CLI process makes a request. Also sends from one process are invisible as events to the other only through `getDifference`.
2. Each process keeps its own pts/seq in memory and overwrites `update_state` on disconnect → the surviving state is whichever process disconnected last (stale for the other) → spurious `getDifference` replays or missed ranges.
3. sqlite: writer holds the file lock from the first `insert or replace into entities` until `save()`; a second writer gets `sqlite3.OperationalError: database is locked` after 5 s; Telethon treats an `OperationalError` in the update loop as fatal and disconnects (`_updates_error`).
4. MTProto anti-replay checks (`network/mtprotostate.py`): "Server sent a very new/old message with ID", "Server replied with a wrong session ID" warnings, dropped packets, salt/time-offset confusion when the same key is used from several places (FAQ).
5. **`AUTH_KEY_DUPLICATED`** (`errors.AuthKeyDuplicatedError`, code 406, base `AuthKeyError`): Telegram's response when it sees the same auth key used from two different clients/IPs concurrently in a way it considers a duplicate (typically a copied `.session`/`StringSession` used on two machines at once, or the same key used with two `initConnection` parameter sets). Telegram **invalidates the key**; every later request fails with `AUTH_KEY_UNREGISTERED`/`AuthKeyNotFound` (`InvalidBufferError` 404 during reconnect → "Server does not know about the current auth key; the session may need to be recreated"). Recovery = delete the session and log in again. Telethon has no special handling beyond raising; tlgr must map it to exit code 4 (AUTH) with a "session invalidated, re-login" message and must never run two long-lived clients on one session file (one process per session; if a second consumer is needed, log in a *second* session for the same account — Telegram allows many sessions per account).

**StringSession** (`sessions/string.py`): `'1' + urlsafe_b64(pack('>B{4|16}sH256s', dc_id, ip, port, auth_key))` (353 chars for IPv4). Contains **only** dc/ip/port/auth key — no entities, no update state, no takeout id. Export: `StringSession.save(client.session)`; import: `TelegramClient(StringSession(s), …)`; to turn a string into a file session: `MemorySession`→`SQLiteSession` copy via `session.set_dc()` + `session.auth_key = …` + `save()`. Importing a StringSession from another Telethon/Pyrogram-like tool is fine as long as the format matches (Pyrogram's differs). Leaking the string = full account access.

**No file locking** exists in Telethon; tlgr must implement its own advisory lock (`fcntl.flock` on `<session>.lock`) around any process that opens a session, and refuse/redirect (via daemon IPC) when locked.

**Other session facts**: `Session.set_dc/dc_id/server_address/port/auth_key/takeout_id/get_update_state/set_update_state/get_update_states/process_entities/get_input_entity/cache_file/get_file/save/close/delete/clone` is the abstract API (`sessions/abstract.py`); `MemorySession` stores the same in dicts (in-memory entity rows are `(id, hash, username, phone, name)`); exported DC senders (file downloads from other DCs, `editInlineBotMessage`, stats) authorize with `auth.exportAuthorization`/`importAuthorization` and are dropped after 60 s idle (`_DISCONNECT_EXPORTED_AFTER`); the main session only ever stores one DC's key.

## 5. Files

**Upload** (`upload_file` / `_file_to_media` / `send_file`):
* Inputs: path/`Path`, `bytes`, any object with `read()` (aiofiles ok; non-seekable streams are read fully into memory), `InputFile`/`InputFileBig` (already uploaded), a `Message`/`MessageMedia*`/`Photo`/`Document` (re-sent without upload via `utils.get_input_media`), `http(s)://` URL (`InputMedia{Photo,Document}External`, server-side fetch), legacy bot-API file id string.
* Part size: `utils.get_appropriated_part_size`: ≤100 MB → 128 KB, ≤750 MB → 256 KB, else 512 KB; must be a multiple of 1 KB and divide 512 KB; `part_size_kb` overridable. Files >10 MB use `upload.saveBigFilePart(file_id, part, total_parts, bytes)` → `InputFileBig(id, parts, name)`; smaller use `upload.saveFilePart` + MD5 → `InputSizedFile` (an `InputFile` with `md5_checksum`). Parts are uploaded **sequentially** on the main connection (no parallel queues; official docs recommend parallel queues on extra connections). File name without extension gets one guessed from content (`utils._get_extension`) to avoid `PHOTO_EXT_INVALID`.
* Size limits: server-side via app config `upload_max_fileparts_default`/`upload_max_fileparts_premium` (`docs/api/api__files.md`; 4000/8000 parts × 512 KB = 2 GB / 4 GB in official clients). Telethon does not pre-check; the server answers `FILE_PARTS_INVALID`. `FLOOD_PREMIUM_WAIT_X` (slowed non-premium upload) is auto-slept like a flood wait.
* Photo path: `is_image` (by extension/magic) and not `force_document` → `InputMediaUploadedPhoto`; `_resize_photo_if_needed` shrinks to ≤2560 px and converts RGBA→RGB **only if Pillow is importable** (it is not in the venv) — oversized/PNG-with-alpha uploads then fail with `PHOTO_INVALID_DIMENSIONS`/`PHOTO_SAVE_FILE_INVALID`/`IMAGE_PROCESS_FAILED`; send as document or install Pillow.
* Document attributes (`utils.get_attributes`): `DocumentAttributeFilename` always; audio/video metadata (`duration`, `w`, `h`, `title`, `performer`) come from **hachoir** — not installed → videos are sent as `DocumentAttributeVideo(duration=0, w=1, h=1)` (renders as a 1×1 "video" in clients) and audio with `duration=0`. tlgr must pass `attributes=[DocumentAttributeVideo(...)]`/`DocumentAttributeAudio(...)` itself (e.g. from `ffprobe`) or install hachoir. User `attributes` override by class.
* `send_file` params: `caption` (str or list for albums), `force_document`, `mime_type`, `file_size`, `clear_draft`, `progress_callback(sent, total)` (sync or async), `reply_to`, `attributes`, `thumb` (path/bytes/IO uploaded as a separate small JPEG), `allow_cache` (no-op), `parse_mode`, `formatting_entities` (list or list-of-lists for albums), `voice_note` (sets `DocumentAttributeAudio(voice=True)`), `video_note` (`round_message=True`), `buttons`, `silent`, `background`, `supports_streaming`, `schedule`, `comment_to`, `ttl` (self-destruct seconds → `ttl_seconds`), `nosound_video` (True prevents a silent MP4 becoming a GIF; only applied when mime is `video/*`), `send_as`, `message_effect_id`. **No `spoiler` parameter** — build `InputMediaUploadedPhoto(f, spoiler=True)`/`InputMediaUploadedDocument(..., spoiler=True)` and pass it as `file`. No `video_cover`/`video_timestamp`/`live_photo`/`invert_media`/`stickers` either (all raw-only). Albums: lists are chunked into 10, each item uploaded with `messages.uploadMedia` then `messages.sendMultiMedia`; mixed photo/video ok; documents in albums require `force_document` consistency.
* `upload_file(key=, iv=)` AES-IGE encrypts parts (secret chats/passport), not needed by tlgr.

**Download** (`download_media`, `download_file`, `iter_download`, `download_profile_photo`):
* `download_media(message|media|bot-file-id, file=None|path|dir|bytes|IO, *, thumb=None, progress_callback=None)`: photos (`Photo`, incl. `video_sizes` → `.mp4`), documents, contacts (→ `.vcard`), web documents (needs `aiohttp` — present), `MessageService` chat-photo actions, webpage previews (`webpage.document or photo`). Returns the path (auto-named `photo_<date>.jpg`, `video_…`, filename from `DocumentAttributeFilename`, `performer - title` for audio, `voice_…`) or `bytes` when `file=bytes`. `thumb=None` → largest size; `int` → index into sizes sorted small→large (0 smallest, -1 largest); `str` → size type (`'s','m','x','y','w'`, `'v'`/`'u'` video sizes); `PhotoSize` object; stripped/cached sizes are written from inline bytes without a request (`utils.stripped_photo_to_jpg`). Progressive sizes use `max(sizes)` as the size hint.
* `download_file(input_location, file=None, *, part_size_kb=None, file_size=None, progress_callback=None, dc_id=None, key=None, iv=None)`: `upload.getFile(location, offset, limit)` chunks of `MIN_CHUNK_SIZE=4096` multiples up to `MAX_CHUNK_SIZE=512 KB` (default part 64 KB when size unknown), sequential; `FileMigrateError` → borrowed exported sender for that DC; `upload.FileCdnRedirect` → CDN client (`upload.getCdnFile`, AES-CTR decrypt, `reuploadCdnFile` on `CdnFileReuploadNeeded`) — CDN is refused for bots. `TimedOutError` sleeps 1 s and retries.
* `iter_download(file, *, offset=0, stride=None, limit=None, chunk_size=None, request_size=512K, file_size=None, dc_id=None)`: async generator of `bytes`/`memoryview`; supports resume (`offset`), ranged reads (`limit` counts chunks), and is the building block for tlgr's own parallel/ranged downloads (use several `iter_download` with different offsets; each borrows the same exported sender per DC).
* **File references** (`docs/api/api__file-references.md`): `InputPhoto/InputDocument/*FileLocation` need the `file_reference` bytes seen in the message; they expire (hours). `download_media(message)` remembers `(input_chat, message.id)` and on `FileReferenceExpiredError`/`FilerefUpgradeNeededError` refetches the message mid-download (`_DirectDownloadIter`); `download_media(bare Document)` cannot recover — tlgr should always keep the message id + chat and refetch (`client.get_messages(chat, ids=id)`) before sending/downloading old media, and never persist `InputDocument` objects long-term.
* `download_profile_photo(entity, file=None, *, download_big=True)` → `InputPeerPhotoFileLocation(peer, photo_id, big)` (works with min hashes); falls back to `channels.getFullChannel().chat_photo` on `LocationInvalidError`; animated profile videos need `download_media(full.profile_photo)` with a `'v'`/`'u'` thumb.
* Speed: pure-Python AES (`pyaes`) is used unless `cryptg` (or a working `libssl` via ctypes) is available — install `cryptg` for multi-MB/s transfers.

## 6. Formatting

**Markdown (Telethon "v1", `extensions/markdown.py`, default `parse_mode`)**: delimiters `**bold**`, `__italic__`, `~~strike~~`, `` `code` ``, ```` ```pre``` ```` (language never set), `[text](url)` with `tg://user?id=N` → mention; no nesting inside code; **no** underline, spoiler, blockquote, custom emoji, or escaping (a literal `**` cannot be sent; strip or use `parse_mode=None`). Not Bot-API MarkdownV2. `unparse` renders only these plus `MentionName` as `[name](tg://user?id=)`; every other entity (spoiler, underline, blockquote, custom emoji, pre language) is dropped silently — unsuitable as tlgr's canonical output format.

**HTML (`extensions/html.py`)**: `<b>/<strong>`, `<i>/<em>`, `<u>`, `<s>/<del>`, `<code>`, `<pre>` with optional `<code class="language-x">` (sets `MessageEntityPre.language`), `<blockquote>` and (1.44) `<blockquote expandable>` → `collapsed=True`, `<a href>` (`mailto:` → Email; href identical to text → `Url`; else `TextUrl`; `tg://user?id=` → mention), `<tg-emoji emoji-id="…">` → `MessageEntityCustomEmoji`. **Not parsed**: `<tg-spoiler>`/`<span class="tg-spoiler">` (Bot-API spoiler syntax) — the text is kept but no `MessageEntitySpoiler` is produced; add it via `formatting_entities`. `unparse` covers bold/italic/code/underline/strike/blockquote(+expandable)/pre/email/url/text-url/mention-name/custom-emoji, escapes HTML, but **drops spoilers** and the newer entities (`FormattedDate`, `Diff*`, `BankCard`, `Cashtag`, `Phone`, `Hashtag`, `BotCommand`, `Mention` are left as plain text). Entities are sorted by offset; zero-length ones are dropped (`_parse_message_text` also drops them, #3884).

**Entities in 1.44 (`types.MessageEntity*`)**: Unknown, Mention, Hashtag, BotCommand, Url, Email, Bold, Italic, Code, Pre(language), TextUrl(url), MentionName(user_id), InputMessageEntityMentionName(InputUser), Phone, Cashtag, Underline, Strike, BankCard, Spoiler, CustomEmoji(document_id), Blockquote(collapsed), FormattedDate, DiffInsert/DiffReplace/DiffDelete (new in L227). Offsets are UTF-16 units (`helpers.add_surrogate`/`del_surrogate`/`within_surrogate`, `helpers.strip_text`).

**Recommendation for output**: emit `text` + the raw `entities` list (JSON via `entity.to_dict()`) and, optionally, a tlgr-side renderer to Bot-API-compatible HTML/MarkdownV2 that covers spoiler/custom-emoji/blockquote; keep `client.parse_mode = None` inside tlgr and parse explicitly per command (`--parse md|html|none`).

**Limits** (server-enforced, Telethon does not check): 4096 UTF-16 units per text message (`MESSAGE_TOO_LONG`), 1024 caption (2048 premium; `MEDIA_CAPTION_TOO_LONG`), ≤100 entities; `utils.split_text()` helps.

## 7. Known bugs / pitfalls (tlgr must handle)

Errors: 515 named RPC error classes + 18 regex ones (`FLOOD_WAIT_X`→`FloodWaitError.seconds`, `FLOOD_PREMIUM_WAIT_X`, `SLOWMODE_WAIT_X`, `FLOOD_TEST_PHONE_WAIT_X`, `TAKEOUT_INIT_DELAY_X`, `2FA_CONFIRM_WAIT_X`, `PHONE/NETWORK/USER/FILE/STATS_MIGRATE_X` (`.new_dc`/`.dc`), `FILE_PART_X_MISSING` (`.which`), `EMAIL_UNCONFIRMED_X` (`.code_length`), `PASSWORD_TOO_FRESH_X`, `SESSION_TOO_FRESH_X`, `INTERDC_X_CALL(_RICH)_ERROR`, `PREVIOUS_CHAT_IMPORT_ACTIVE_WAIT_XMIN`). Unknown messages fall back to the code base class (`BadRequestError` 400, `UnauthorizedError` 401, `ForbiddenError` 403, `NotFoundError` 404, `AuthKeyError` 406, `FloodError` 420, `ServerError` 500/-500/-503, `InvalidDCError` 303, `TimedOutError`); negative codes are normalised. Every RPC error has `.request`, `.code`, `.message`. Map for tlgr exit codes: `FloodWaitError/SlowModeWaitError/PeerFloodError` → 7 (wait_seconds), `Unauthorized*/AuthKey*/SessionRevoked/SessionExpired/UserDeactivated(Ban)` → 4, `ChatWriteForbidden/UserIsBlocked/ChatAdminRequired/ChannelPrivate/UserPrivacyRestricted/Forbidden*` → 6, `PeerIdInvalid/UsernameNotOccupied/UsernameInvalid/ChannelInvalid/MessageIdInvalid/ValueError("Could not find the input entity")` → 5, `ServerError/TimedOutError/OSError/ConnectionError` → 8.

1. **Entity cache misses**: any id not present in `entities`/in-memory cache → `ValueError`; ids are per-account (access hashes differ per account); `-100`-prefixed ids required for channels; usernames hit the network each time via `get_entity` (use `get_input_entity` first); phone lookups scan the whole contact list; invite links only resolve if already joined; `min` users need `*FromMessage` inputs which Telethon never builds.
2. **`iter_dialogs`**: dialogs with unknown peers silently skipped; pinned dialogs break date ordering (Telethon works around it); `offset_date` may be ignored server-side; no stable cursor beyond `(offset_date, offset_id, offset_peer)`; `folder=` is archive only; `total` counts all dialogs even when filtered; hash always 0 (full payload every time).
3. **`iter_messages`**: min/max id emulation, extra request with `filter`+`offset_date`, `RPC_CALL_FAIL` with `filter`+`from_id`, `SearchGlobal` cannot reverse, short pages from restricted channels, `MessageEmpty` gaps, `ids=` chunking waits 10 s when >300 ids, `ChatAdminRequiredError` on some searches, `wait_time` auto-1s for big limits (slow), no forum-topic/saved-sub-dialog filters.
4. **`flood_sleep_threshold`**: sleeps *inside* the call (tlgr's 120 s means a CLI command may hang 2 minutes with no output; expose `--flood-wait-max`, default lower for interactive commands, and emit progress to stderr); `_flood_waited_requests` makes later calls of the same constructor pre-fail/sleep even in another coroutine; `SlowModeWaitError` is not remembered per chat; flood waits <3 s are ignored.
5. **`request_retries`**: retries `ServerError`, `RpcCallFail`, `RpcMcgetFail`, `InterdcCall*`, `TimedOutError` with fixed 2 s sleeps; after exhaustion raises `ValueError` unless `raise_last_call_error=True` (set it). Requests that "can always fail" (search) may burn retries.
6. **Auto-reconnect**: `connection_retries=5` × `retry_delay=1` — after 5 failed reconnects the client is permanently disconnected (`disconnected` future raises; `is_connected()` False; every call raises `ConnectionError('Cannot send requests while disconnected')`); no backoff (fixed delay → reconnect storms on flaky links); after a successful reconnect pending requests are re-sent and only `get_me()` is issued (no catch-up); `_keepalive_loop` pings every ~60 s and triggers reconnect on silence. tlgr's daemon already tracks per-account health; it should also call `catch_up()` after reconnects and consider `connection_retries=None` with its own backoff supervisor.
7. **Proxies**: needs `python-socks` (preferred) or `PySocks`; formats `(type, host, port, rdns, user, pass)` or dict; MTProxy via `connection=ConnectionTcpMTProxyRandomizedIntermediate` + `proxy=(host, port, secret)` (`tcpmtproxy.py`, secret in hex/base64, `dd`/`ee` prefixes normalised) — the MTProxy code is marked experimental; SSL-requiring proxies unsupported; exported senders reuse the proxy. `use_ipv6=True` switches the bootstrap DC address (`2001:67c:4e8:f002::a`) and is persisted in `sessions.server_address` (a session created with IPv4 is re-pointed when `use_ipv6` changes). None of the proxy libs are installed in the venv.
8. **asyncio loop**: the loop must not change after `connect()` (`RuntimeError`); `asyncio.run()` per command is fine only if the client is created *and* connected inside that run; `telethon.sync` monkey-patches every coroutine method to run the loop when idle — do not import it in tlgr (breaks inside running loops, and `RequestIter.__iter__` raises if the loop is running). `helpers.get_running_loop()` in 1.44 creates a loop when none exists — avoid relying on it. `client.loop` is the connected loop. Ctrl-C: `run_until_disconnected()` swallows `KeyboardInterrupt` and disconnects; a bare `disconnect()` from a signal handler must be awaited.
9. **Big files**: no parallelism; pure-Python AES without `cryptg`; 2 GB/4 GB caps; `FILE_PART_X_MISSING` if a part upload timed out (server dropped temp storage) — retry the whole upload; `file_reference` expiry mid-download only auto-recovers when a `Message` was passed; `download_media` of a `MessageMediaWebPage` picks document over photo; `thumb=` semantics differ between photos (`sizes`) and documents (`thumbs`).
10. **sqlite locking / two processes** (§4): "database is locked" is fatal for the update loop; entities are written on every response without commit until `save()` (long write locks); no advisory lock; `AUTH_KEY_DUPLICATED` when a copied session is used elsewhere.
11. **Own actions are invisible to handlers** (§3) and `MessageEdited` fires on reaction/view changes; `MessageDeleted` for private/basic-group chats has no `chat_id`; `ChatAction` ignores most modern service messages (topics, gifts, calls, TTL changes, join requests, boosts…); `UserUpdate.typing` has no topic id; `NewMessage` ignores `MessageService` entirely.
12. **`start()` and `_start` print to stdout/stderr**; `kick_participant` sleeps 0.5 s; `pin_message` defaults to silent; `edit_permissions` semantics are inverted (True = allowed); `edit_admin(is_admin=True)` grants only the 10 legacy rights; `get_permissions` lacks the newer rights; `iter_participants(aggressive=)` is dead; `forward_messages(as_album=)` is dead; `send_code_request(force_sms=)` is dead.
13. **Entity/update-state persistence** only on `disconnect()` — a SIGKILL'd daemon (launchd stop with SIGKILL, crash) loses pts and cached hashes; tlgr should periodically call `await client._save_states_and_entities(); client.session.save()` (private API; wrap with try/except and pin the Telethon version) or run `catch_up()` on start with the last-known state.
14. **Layer skew / "Could not find a matching Constructor ID"** (`TypeNotFoundError`): Telegram may send constructors the client doesn't know (e.g. after the same session is used by a newer client, or big-channel updates in older layers per `docs/api/api__invoking.md`); the update loop treats it as fatal. Keep exactly one client per session and pin the Telethon version.
15. **Time skew**: system clock off by more than ~30 s → "very new/old message" warnings, requests silently dropped/`BadMessageError` 16/17; Telethon corrects `time_offset` from server msg ids but only after the first reply.
16. **`get_dialogs(limit=None)` on large accounts** iterates 100 per request with no wait — flood-wait risk; the `search` in `iter_participants` for basic chats/users is client-side (fetches everything).
17. **`Message.file.id` / bot-API file ids** are deprecated and may not round-trip; don't expose them as stable identifiers.
18. **Photos as documents**: `force_document=True` on an image still uploads with `is_image=True` semantics (sends `InputMediaUploadedDocument(force_file=…)` only when `not is_image` in `get_attributes`; the file is still sent as a document because `as_image=False`) — verify output with `message.document`.
19. **`download_media(file=<dir>)`** appends an auto-generated name; passing an existing *file* path overwrites; reserved Windows names sanitised only on Windows.
20. **`delete_dialog` on channels** does not delete history for the other side; for private chats `revoke=False` keeps the other side's copy; bots can't delete private dialogs.
21. **`sequential_updates=True`** + slow webhook/gateway handlers = growing backlog and delayed `getDifference`; consider processing in a bounded worker pool while keeping order per chat.
22. **`entity_cache_limit`** (5000) triggers a synchronous flush to sqlite inside the update loop (latency spike) and warns if it cannot shrink — raise it for accounts with many chats.

### 8.4 How tlgr could call layer-229 features without waiting for Telethon

Telethon deserialises with `BinaryReader.tgread_object()` → `telethon.tl.alltlobjects.tlobjects[constructor_id]` and serialises via each class's `_bytes()`; the negotiated layer is the module constant `LAYER` imported into `client/telegrambaseclient.py` and sent as `InvokeWithLayerRequest(LAYER, InitConnection(...))` at connect. Three ingredients:

1. **Custom classes**: subclass `telethon.tl.tlobject.TLRequest` (functions) / `TLObject` (types) with `CONSTRUCTOR_ID` from `api.tl`, `SUBCLASS_OF_ID = zlib.crc32(b'<ResultType>')`, `__init__`, `_bytes()` (flags packed `struct.pack('<I', flags)`, ints `<i`, longs `<q`, strings via `TLObject.serialize_bytes`, vectors as `b'\x15\xc4\xb5\x1c' + '<i' len + items`), `from_reader(cls, reader)` (mirror the generated code, e.g. `SendReactionRequest` in `tl/functions/messages.py`), `resolve(self, client, utils)` to convert entity-likes into input peers, and `read_result(reader)` when the result is a bare `Bool`/`Vector`. Register every **type** the result can contain in `alltlobjects.tlobjects[cid] = cls` (functions need no registration). For 229's changed core types (`user`, `channel`, `keyboardButton`, `replyInlineMarkup`, `botCommand`, …) the practical approach is `class User229(types.User): CONSTRUCTOR_ID = 0xb1b8cc83` with a `from_reader` that reads the extra field and returns a `types.User` instance (isinstance checks all over Telethon keep working), registered under the new id — Telethon's `tl/patched/__init__.py` does exactly this for `Message`.
2. **Layer negotiation**: (a) per-connection — set `telethon.client.telegrambaseclient.LAYER = 229` *before* `connect()` (and in exported senders it is read from the same module); Telegram will then send 229 constructors everywhere, so **every** changed constructor in 8.3 must be registered or the update loop dies with `TypeNotFoundError`; (b) per-request — wrap only the new call: `await client(functions.InvokeWithLayerRequest(229, CustomRequest(...)))`. The official docs describe `invokeWithLayer` as the mechanism that sets the layer "for the query" (`docs/method/invokeWithLayer.md`, `docs/api/api__invoking.md` says the value saved by `initConnection` is used for *future* requests, i.e. later un-wrapped requests remain at 227). The response to the wrapped query is serialised at 229, so its result type and everything nested (e.g. `messages.Chats` with `community`, `Updates` with `user`/`channel`) must be registered too; `Bool` results (`communities.togglePeerLink`, `ephemeral.deleteMessage`) work without any type registration. Empirically verify with `stringify()` before shipping — Telegram does not document per-request layer switching as supported, and the update stream stays at the session layer.
3. **Alternative**: vendor a regenerated `telethon/tl` (run `telethon_generator` from the repo clone with tdesktop's `api.tl` at layer 229 plus Telethon's `errors.csv`/`methods.csv`) and pin that fork; the generator lives in `refs/telethon/telethon_generator` (`python setup.py gen`). This is what a layer bump in Telethon itself is, and it keeps `Button`/`build_reply_markup`/`Message.click` needing a rewrite for the new keyboard model (they construct `KeyboardButtonCallback` etc.).

Practical ordering: nothing in 8.1 is on the critical path of a user-facing CLI today (communities/ephemeral are brand-new server features; Firebase is Android-only; AI rich compose needs Premium), so tlgr should stay on 227, implement the custom-class mechanism as a documented escape hatch, and revisit when Telethon publishes the next layer.
